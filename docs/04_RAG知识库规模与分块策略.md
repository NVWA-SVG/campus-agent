## 2. “RAG 库有多大”需要分口径回答

面试官问“库有多大”时，可能同时在问业务数据量、索引规模和磁盘占用，不能把它们混成一个数字。

| 口径 | 当前规模 | 是否属于知识正文 |
|---|---:|---|
| 内置 Markdown | 5 份，2454 字节 | 是 |
| 用户上传文档 | 0 份 | 是，但当前为空 |
| 可检索 Chunk | 10 个，正文共 704 字符 | 是 |
| 向量缓存 | 4 个文件，约 98.8 KiB | 否，是索引缓存 |
| BGE 模型 | 约 91.9 MiB | 否，是 Embedding 模型参数 |
| 会话 SQLite 主文件和共享内存 | 当前共约 84 KiB | 否，是会话 Checkpoint |
| Chrome/PDF 运行缓存 | 大小会变化 | 否，与知识库规模无关 |

当前动态知识目录 `.campus_agent_data/knowledge` 中只有 SQLite、SHM 和 WAL 文件，没有任何上传文档对应的目录和 `metadata.json`，所以用户上传文档数量确定为 0。

向量缓存也不等于知识正文。项目可能因为模型指纹、配置或测试运行留下多个缓存文件；当前内置知识库只有 10 个 Chunk。BGE 模型更不能算成“92 MB 的知识库”，因为它是通用向量模型，不包含本项目的校园业务资料。

## 4. 文档进入 RAG 的完整流程

项目的知识摄取流程如下：

```text
Markdown / TXT / PDF
→ 校验文件名、扩展名、Content-Type 和大小
→ 提取并规范化文本
→ 按 Markdown 标题进行语义分段
→ 对过长段落进行带重叠的长度切分
→ 生成 Chunk ID 和 Metadata
→ 构建 BM25 与向量候选索引
→ 构建完成后原子替换当前不可变快照
```

不同文件类型进入统一分块器前会先标准化：

- Markdown：保留原来的一级至三级标题；如果没有一级标题，则使用文件名补充一级标题。
- TXT：要求 UTF-8 编码，并使用文件名生成一级标题。
- PDF：本地提取文本，文档名作为一级标题，每一页转换成 `## 第 N 页`；扫描版 PDF 当前不做联网 OCR。

这样三种文件最终都变成具有标题层次的 Markdown 文本，再走同一套分块逻辑。

## 5. 当前项目的 RAG 分块策略

### 5.1 第一层：按标题进行语义分块

分块器识别 Markdown 的一级、二级和三级标题：

```regex
^(#{1,3})\s+(.+?)\s*$
```

处理规则如下：

1. 一级标题作为文档标题；
2. 二级或三级标题开始一个新的业务章节；
3. 遇到下一个标题时，将此前积累的正文写入一个 Chunk；
4. Chunk 标题使用“文档标题 - 章节标题”；
5. 四级及以下标题目前不会被识别成新的结构边界，而是保留在正文中。

项目优先使用标题边界，是因为校园指南通常天然按照“办理条件、申请流程、所需材料、异常处理”等业务语义组织。按标题切分比固定每 N 个字符截断更容易保留一项流程的完整上下文。

### 5.2 第二层：长章节按字符数继续切分

如果一个标题章节的正文不超过 1200 个字符，就直接生成一个 Chunk。如果超过 1200 个字符，则继续切分：

- 单块最大长度：1200 个字符；
- 相邻块重叠：120 个字符；
- 优先断点：换行、中文句号、感叹号、问号、英文分号和中文分号；
- 自然断点只在当前窗口后半部分寻找，避免生成特别短的碎片；
- 找不到合适自然断点时，才在 1200 字符硬边界切开。

伪代码可以概括为：

```text
start = 0
while start < 正文长度:
    hard_end = min(start + 1200, 正文长度)
    在 [start + 600, hard_end] 中向前寻找自然标点
    找到标点 → 在标点后切分
    未找到   → 在 hard_end 切分
    下一块从 end - 120 开始
```

Overlap 的作用是避免办理条件、否定词或关键时间刚好落在边界两侧。例如上一块结尾出现“符合以下条件”，下一块才列出具体条件；保留 120 个字符可以让两块都拥有一部分连接语义。

当前规则是字符级而不是 Token 级。它对中文文档简单稳定，但如果以后接入超长中英文混合文档，可以改成 Token-aware 分块，并对表格、列表和附件建立专门的解析规则。

### 5.3 Chunk ID 与 Metadata

Chunk ID 的格式为：

```text
<document-prefix>-<section-index>-<part-index>
```

例如：

```text
campus_card-1-0
```

含义是 `campus_card` 文档的第 1 个正文章节、该章节的第 0 个长度分片。一个章节如果超过 1200 个字符，后续分片会依次使用 `-1`、`-2`。

每个 Chunk 同时携带：

```text
document_id
source_name
domain
category
visibility
version
origin
chunk_index
```

Metadata 用于检索前过滤、权限边界、版本控制和 Citation。过滤在评分以及 BM25 语料统计前完成，避免 private 或无关文档影响公开候选的 IDF。

## 6. 项目中的真实分块例子

### 6.1 原始校园卡文档

`campus_card.md` 的结构是：

```markdown
# 校园卡服务指南

## 挂失与补办

校园卡、饭卡遗失后，应立即登录校园卡服务平台办理挂失，避免余额被他人使用。完成挂失后，携带本人有效身份证件前往校园卡服务中心申请补办，新卡领取方式以服务中心通知为准。

## 解挂与密码

找回原校园卡且尚未补办新卡时，可以在校园卡服务平台申请解挂。忘记密码或连续验证失败时，应携带本人证件到服务中心重置，不能委托他人代办身份验证。
```

### 6.2 实际生成的两个 Chunk

第一个 Chunk：

```text
chunk_id: campus_card-1-0
title: 校园卡服务指南 - 挂失与补办
source: campus_card.md#校园卡服务指南 - 挂失与补办
content_length: 83
content: 校园卡、饭卡遗失后，应立即登录校园卡服务平台办理挂失，避免余额被他人使用。完成挂失后，携带本人有效身份证件前往校园卡服务中心申请补办，新卡领取方式以服务中心通知为准。
```

第二个 Chunk：

```text
chunk_id: campus_card-2-0
title: 校园卡服务指南 - 解挂与密码
source: campus_card.md#校园卡服务指南 - 解挂与密码
content_length: 71
content: 找回原校园卡且尚未补办新卡时，可以在校园卡服务平台申请解挂。忘记密码或连续验证失败时，应携带本人证件到服务中心重置，不能委托他人代办身份验证。
```

这里没有触发第二层长度切分，因为两个章节分别只有 83 和 71 个字符，都小于 1200。当前 10 个内置 Chunk 全部较短，所以实际数据中尚未触发 overlap；但上传长 Markdown、TXT 或 PDF 时会使用相同的 1200/120 策略。

### 6.3 用户问题如何命中 Chunk

用户提问：

```text
饭卡丢了怎么重办？
```

典型执行过程：

```text
原问题
→ BM25 捕获“饭卡”等精确词
→ 向量召回识别“丢了、重办”与“遗失、补办”的语义关系
→ 必要时 Rewrite 将“一卡通/饭卡、丢了、重办”规范为“校园卡、遗失、补办”
→ 命中 campus_card-1-0
→ 回答引用该 Chunk 的结构化 Citation
```

分块按“挂失与补办”这一完整业务章节组织，所以命中后可以同时获得挂失、证件要求、办理地点和领取说明，而不是只取到一句残缺内容。

## 7. 分块后的检索方式

分块完成后，项目不是只使用向量相似度，而是使用混合检索：

```text
用户 Query
├─ BM25：关键词、编号、时间等精确召回
└─ Vector：语义相似召回
          ↓
Weighted Reciprocal Rank Fusion
          ↓
Top-k Chunk + Citation
```

- BM25 对标题进行额外加权，适合校园卡、课程代码和时间等精确事实；
- 向量通道可使用本地 Hashing 基线，或锁定版本的 `BAAI/bge-small-zh-v1.5`；
- 两路结果使用 RRF 按排名融合，词法权重为 0.55，向量权重为 0.45；
- 向量模型或缓存发生异常时，系统降级到 BM25，不让整个知识库失效。

分块质量会直接影响两路召回：块太大容易混入无关主题，块太小又会丢失办理条件与上下文。目前“标题语义块 + 1200 字符上限 + 120 字符重叠”是针对校园指南类短文档的折中。

## 8. 容量限制与工程边界

动态知识库当前设置了以下安全上限：

| 限制项 | 当前值 |
|---|---:|
| 单个上传文件 | 10 MiB |
| 全部上传文件 | 100 MiB |
| 上传文档数量 | 100 份 |
| 单个 PDF 页数 | 100 页 |
| 单文档提取文本 | 100 万字符 |
| 单个 Chunk | 最多 1200 字符 |
| Chunk overlap | 120 字符 |

这些值是上传和资源保护边界，不代表当前已经存有 100 MB 文档。

当前索引采用进程内 BM25、向量矩阵和完整不可变快照。上传、删除后会在候选快照中重新构建索引，成功后再原子替换，因此适合求职演示和中小规模知识库，但不适合直接宣称支持几十万或上百万 Chunk。

如果继续扩容，可以按以下方向升级：

1. 使用 Qdrant、Milvus、pgvector 或 Elasticsearch 保存大规模向量与倒排索引；
2. 将全量重建改为增量索引和后台任务；
3. 增加 Token-aware、父子 Chunk、表格和 OCR 分块；
4. 使用真实查询集评估不同 Chunk 大小与 overlap；
5. 增加租户、文档和 Chunk 级访问控制；
6. 对版本、过期文档和重复内容建立生命周期管理。

## 9. 面试回答模板

### 9.1 30 秒回答

> 当前知识库是架构验证规模，共有 5 份内置校园业务文档，分块后是 10 个 Chunk，暂时没有用户上传资料。分块采用两层策略：先按 Markdown 一级到三级标题划分语义章节，章节超过 1200 个字符时再按自然标点切分，并保留 120 个字符重叠。每个 Chunk 都带文档 ID、业务分类、版本、可见性和来源等 Metadata。检索使用 BM25 与 BGE 向量双路召回，再通过 RRF 融合。当前数据量虽然小，但上传、分块、检索、降级、Citation 和原子重建链路是完整的。

### 9.2 面试官追问“为什么只有 10 个 Chunk”

> 因为当前重点是验证 Agent 与 RAG 的工程闭环，不是伪造大规模数据。小数据便于为每个 Query 标注期望 Chunk，并验证 Recall、MRR、No-hit 和 Citation。生产化前需要接入经过授权的校内文档，再重新评估分块参数和扩展索引后端。

### 9.3 面试官追问“为什么不用固定长度切分”

> 校园办事文档通常按业务标题组织，先按标题切分能保留“办理条件、材料、流程”这样的完整语义单元。只有章节过长时才按长度继续切，既控制检索粒度，也避免一开始就把流程切碎。

### 9.4 面试官追问“92 MB 是不是知识库大小”

> 不是。约 92 MB 是 BGE Embedding 模型参数，真正的内置业务文档只有约 2.4 KiB，切分后是 10 个 Chunk；向量缓存约 98.8 KiB。模型、索引缓存、知识正文和会话数据库必须分开统计。
