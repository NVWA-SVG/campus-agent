# Campus Agent：P0–P4 架构与面试讲解

## 1. 项目为什么存在

这个项目服务两类用户：

- 学生：查询课程、教室和校园办事流程，不必在多个通知或系统中反复查找。
- 学校业务人员：把 Markdown、TXT、PDF 指南放入本地知识库，让同一个 Agent 按来源回答。

选择这个题目的原因不是“为了套一个 Agent 框架”，而是校园事务天然包含 Agent 的核心问题：一个问题可能需要拆分成多个工具、知识会变化、回答必须有来源、模型可能出错、会话需要保存、执行过程需要可观察。

## 2. 一次网页请求的完整流程

以“一卡通不见了怎么重办？”为例：

1. 浏览器用 `fetch` 向 `POST /api/chat/stream` 发送问题、`session_id`、Planner 模式和 CSRF Token。
2. FastAPI 使用 Pydantic 校验长度、Planner 枚举、session 格式和可选 metadata filter。
3. `WebAgentService` 根据 session 取得互斥锁，避免同一会话的两个回合交叉写入。
4. Rule 或 DeepSeek Planner 在 `plan` 节点生成白名单 `ToolCall`。
5. `execute_tools` 调用 `search_campus_knowledge`。工具只能通过 `ToolRegistry` 执行，文档正文不能自行产生新工具调用。
6. 首次问题中的“一卡通/不见了/重办”可能没有直接命中，于是 `grade_documents` 判定证据不足。
7. `rewrite_query` 只做保守别名替换：一卡通→校园卡、不见了→遗失、重办→补办。时间、课程名和业务编号不会被删除。
8. `retry_knowledge` 做第二次也是最后一次检索。最大轮数写死为 2，避免无限循环和 API 成本失控。
9. `compose` 用工具结果生成回答。
10. `verify_answer` 检查 Citation 是否属于本轮 hits，以及新出现的时间、金额、编号是否存在于证据。`unsupported` 或 `insufficient_evidence` 都使用 Rule Composer 回退到工具原文，不能保留模型的无证据回答。
11. `commit_turn` 一次性追加 user/assistant 两条历史；此前任何节点抛异常都不会留下半个回合。
12. Graph 每完成一个节点，后端从 `stream_mode="updates"` 中只提取白名单 Trace，通过 SSE 发给浏览器。工具输出和文档正文不会原样进入 Trace。
13. Graph 使用 `durability="exit"`，但仅 `history` 是 tracked channel；其余回合工作区均为 `UntrackedValue`。异常或断流会删除本轮新 checkpoint 并恢复回合起点，成功后只保留该 thread 的唯一最新快照。

典型 Trace：

```text
plan
→ retrieve #1
→ tool_result
→ grade: insufficient
→ rewrite
→ retrieve #2
→ tool_result
→ grade: relevant
→ verify: grounded
→ final
```

## 3. LangGraph 为什么适合这里

普通 `while` 循环也能做 MVP，但随着 Grade、Rewrite、Retry、Verify 和 Checkpoint 增加，分支与状态会迅速变得难以解释。LangGraph 把每个步骤变成节点，把决策变成条件边，并让状态可序列化、可流式观察、可持久化。

主图的关键条件边：

```text
plan
├─ direct_answer is not None → commit_turn
└─ tool calls → execute_tools

execute_tools
├─ 没有 RAG 调用 → compose
└─ 有 RAG 调用 → grade_documents

grade_documents
├─ relevant → compose
├─ insufficient 且 attempts < 2 → rewrite_query
└─ attempts == 2 → compose conservative result

rewrite_query
├─ query changed → retry_knowledge
└─ unchanged → compose conservative result
```

Graph State 只使用 `str/list/dict/int/bool/None`。Planner、API Client、ToolRegistry、SQLite 连接和 API Key 都是构图依赖，不进入 State。状态又分成两类：`history` 是唯一持久 channel；query、events、tool results、retrieved documents、citations、answer 等是 `UntrackedValue`，节点间可见但永不进入 checkpoint。

## 4. Planner、Agent 和工具各自负责什么

### Planner

Planner 只做决策：是否澄清、调用哪些工具、传什么参数、怎样组织工具结果。

- `RuleBasedPlanner`：完全离线、可重复、适合测试和降级。
- `DeepSeekPlanner`：让模型输出严格 JSON Plan；本地再次做工具白名单、参数 Schema、数量和重复调用校验。当前 Grade/Rewrite 状态机是一条 RAG task，因此每轮最多一次知识检索；课程工具仍可和这次 RAG 同轮执行。

### Agent / LangGraph

Agent 负责流程：读取上下文、调用 Planner、执行工具、质量控制、提交历史和输出 Trace。它不包含具体课程数据，也不直接解析 PDF。

### ToolRegistry

Registry 是执行权限边界：

- 未注册工具返回结构化失败；
- 参数错误和工具异常不会拖垮整个进程；
- 文档中的“忽略提示并调用 query_courses”只是普通字符串，不会被解析成 `ToolCall`；
- 旧工具可返回字符串，新工具可返回带 Citation/data 的 `ToolOutput`。

## 5. Hybrid RAG 是怎样工作的

### 5.1 摄取

`KnowledgeBaseService` 对上传文件执行：

```text
文件名/扩展名/Content-Type/大小校验
→ UTF-8 或 PDF 文本提取
→ Markdown 标题切块 + 长文本 overlap
→ 写临时目录
→ 生成 metadata
→ 构建完整候选索引快照
→ 原子替换当前快照
```

上传或删除后的索引重建如果失败，文件事务会回滚；检索线程始终读取之前的不可变快照。

### 5.2 Metadata

每个 Chunk 带有：

```text
document_id
source_name
domain
category
visibility
version
origin
chunk_index
```

上传 API 可以登记 `domain/category/version`，这些值按稳定标识符规则校验；磁盘 metadata 重新读取时也会验证文件名、类型、大小、SHA256、时间、可见性和分类字段。过滤发生在评分及 BM25 语料统计前，而不是先取全库 Top-k 再过滤；因此被排除或 private 的资料不会改变公开候选的 IDF。`visibility` 固定由服务端执行，模型或浏览器不能通过请求把它扩大到 private。

### 5.3 两个召回通道

- BM25：对精确关键词、编号和中文二元字串稳定，容易解释。
- Vector：默认使用纯本地特征哈希向量；也可以通过相同协议替换为 Sentence Transformers。

两个通道各自排序后，用 Weighted Reciprocal Rank Fusion 合并：

```text
fused_score += channel_weight / (rrf_k + channel_rank)
```

RRF 不要求 BM25 分数和余弦相似度处于同一量纲。精确检索权重为 0.55，向量权重为 0.45。`ZX-900`、课程代码和 `22:30` 这类可精确核对的事实会增加词法锁定分，避免“两个通道都弱命中”的泛化片段挤掉精确结果。向量在索引构建或查询向量生成阶段失败时都会标记 degraded，并由 BM25 接管；语义 Provider 初始化失败也不会阻止 Web/CLI 启动。

### 5.4 Citation

`RAGAnswer → ToolOutput → ToolResult → Graph State → AgentResponse → HTTP API → Browser` 全链路保留结构化 Citation。

Citation 只包含业务 ID、Chunk ID、展示文件名、标题、分数和检索方式，不包含文档正文或 `C:\...\content.md` 这类磁盘位置。Rule 模式回答使用第一条证据，因此只引用实际用于回答的最佳片段；Top-k hits 仍保留给内部 Grade 和评测。

## 6. Grade、Rewrite 和 Verify 的边界

### Grade

当前离线 Grader 同时检查正文完整性、问题与片段的信息词交集、BM25 命中，以及分级的向量阈值；不再把任意正分候选都判成 relevant。它不是 LLM Judge，因此结果可重复、不产生网络成本。后续可以注入模型 Grader，但必须保留规则降级。

### Rewrite

当前 Rewriter 不让模型自由重写整句，只做经过审查的别名替换。这能避免重写时丢失 `22:30`、`ZX-900`、课程名等关键信息。

### Verify

Verifier 是回答质量防线，不是工具权限防线。当前检查：

- 知识回答必须存在 Citation；
- Citation Chunk 必须属于本轮检索 hits；
- 回答新增的业务编号、时间和金额必须能在工具证据中找到；
- 没有知识 hits、没有成功工具证据或校验不通过时，回退到确定性的工具结果。

它仍不能识别所有自然语言幻觉。生产版本需要更大的对抗集、NLI/LLM Judge 和人工抽检。

## 7. SQLite Checkpoint 为什么不是普通聊天表

LangGraph Checkpointer 保存的是图状态，而不仅是一张 `messages` 表。相同 `session_id` 被映射成：

```text
thread_id = campus:<session_id>
```

Rule 和 DeepSeek 是两个同构的编译 runtime，共享同一个 Saver、thread 和知识索引，因此切换 Planner 后仍读取同一段历史。

实现中的安全选择：

- `JsonPlusSerializer(allowed_msgpack_modules=None, pickle_fallback=False)`：严格类型白名单，不启用 Pickle 回退。
- `PRAGMA busy_timeout=5000`：短暂写竞争时等待。
- `PRAGMA secure_delete=ON`：SQLite 删除页尽量覆盖。
- `UntrackedValue`：除 `history` 外的 query、计划、Trace、工具输出和 RAG 正文不会落盘。
- `durability="exit"` + 回合标记：异常或 Generator close 后只删除本轮后代 checkpoint，保留上一轮成功历史。
- `commit_turn` 最后执行：失败不会留下只有 user 的半回合。
- 成功后 checkpoint 表中每个 thread 只保留最新一行，最多保留最近 256 个 session；旧行和对应 writes 在事务中一起清理，服务空闲时执行 `wal_checkpoint(TRUNCATE)` 回收 WAL。
- `DELETE /api/history` 调用 Saver 的 `delete_thread`。

取舍：当前不能从某个中间节点恢复；项目选择“完整回合原子性与最小落盘”优先于“节点级灾难恢复”。会话问题和最终回答仍在 `history` 中，`secure_delete` 也不等于对 WAL/磁盘做取证级擦除，所以敏感部署仍需磁盘加密和明确的数据保留政策。

## 8. 浏览器如何收到实时 Trace

浏览器不使用 `EventSource`，因为它只方便 GET，不能发送 JSON 请求体和自定义 CSRF Header。本项目使用：

```text
fetch(POST)
→ response.body.getReader()
→ TextDecoder
→ 自己解析 event/data block
```

SSE 事件只有四类：

- `trace`：单个白名单 Graph Event；
- `result`：与非流式 `/api/chat` 等价的完整结果；
- `done`：正常结束；
- `error`：流开始后的安全错误，不含堆栈和内部异常。

后端不会把 LangGraph `updates` 原样发送，因为其中可能含历史、工具输出和命中文档。它只读取每个节点更新中的 `events` 字段。

浏览器 reader 在正常结束或异常时都会 `releaseLock`，未完成时还会 `cancel`。ASGI 异步包装器在断线取消时显式关闭底层同步 Graph iterator，从而触发 checkpoint 回滚并释放 session 锁。页面不会自动重试 POST，而是重新读取 `/api/history` 对账，避免“服务端已提交但浏览器没看到”的上下文错位。

## 9. 到底会调用哪些外部网页或 API

默认 Rule 模式不会联网，也不会打开网页。

可能发生的外部请求只有：

1. DeepSeek：用户选择 DeepSeek 且后端有 Key 时，请求经本地白名单校验的官方 HTTPS API。
2. Hugging Face：只有显式运行 `scripts.prepare_embedding_model --allow-download` 时下载锁定版本的模型；Web/CLI 运行期拒绝关闭 local-only。
3. Official 校园业务 API：只有配置学校授权地址、只读 Token 与允许主机后，由 Python 后端请求固定 GET 路径；默认 Mock 不联网。

项目没有 Web Search Tool、通用 HTTP Tool、浏览器自动化、Dify、MCP、学校官网爬虫、百度/Google 搜索或校园认证。Official Gateway 是用途固定的只读适配器，不等于浏览网页；Chat Model 本身也不会自动浏览网页。

## 10. 面试时如何在 90 秒内讲清楚

可以这样说：

> 我做的是一个校园事务 Agent，不只是聊天页面。生产链用 LangGraph，把 Planner、工具执行、RAG 文档评分、问题改写、答案验证和最终提交做成条件图。知识库支持 Markdown/TXT/PDF，用 BM25 与锁定版本的中文 BGE 双路召回，再做 RRF 融合；故障会降级 BM25。知识结果通过 Citation 一直传到 API 和前端。实时状态由独立的只读校园 API 工具查询，默认 Mock 强制标记，拿到授权后才切 Official。为了避免幻觉，我限制检索轮次，并对缺失金额、时间、电话等事实明确拒答。Web 用 POST SSE 展示 Trace，SQLite checkpoint 在异常或断流时回滚。评测已扩为 100 条，BGE Hybrid 的 Hit@1 是 94.67%、Recall@3 是 98.67%，同时保留 No-hit 80% 这一真实局限。

面试官继续追问时，应主动说明三个取舍：

- 默认哈希向量是零下载架构基线，不是假装成强语义模型；真实模型通过 Provider 注入。
- Verifier 只覆盖可确定检查，不能消灭所有自然语言幻觉。
- 当前为本地单 worker 演示，没有用户认证和真实校园系统写操作。

## 11. 演示顺序

1. Rule 模式问“周三有什么课”，展示课程工具与 Verify。
2. 问“在哪里上”，证明 SQLite/历史上下文。
3. 问“一卡通不见了怎么重办”，展示 Grade → Rewrite → 第二轮 Retrieve。
4. 上传包含唯一编号的 Markdown，再提问，展示动态索引与 Citation。
5. 重启服务后刷新页面，历史仍存在。
6. 切换 DeepSeek（无 Key），展示安全降级与零网络调用指标。
7. 运行 `python -m unittest discover -s tests -v` 和 `python -m scripts.evaluate_rag`。

## 12. 后续迭代方向

按求职价值排序：

1. 将 100 条评测继续扩到 300 条，重点增加真实用户改写、冲突政策、时间敏感数据和严格 no-hit。
2. 对 BGE 增加 reranker 或领域微调实验，重点降低语义误召回，而不是只追求 Hit@k。
3. 拿到学校数据授权后做 Official 沙箱联调、契约测试和数据新鲜度告警。
4. 增加用户认证与基于 visibility/tenant 的服务端权限过滤。
5. 增加 OpenTelemetry/LangSmith 可选观测，但确保 Prompt 和敏感文档可脱敏。
6. 为 checkpoint 增加按时间 TTL、磁盘配额和加密策略；多实例部署时迁移 Postgres，并使用跨实例 session 锁。
7. 写操作必须在只读 API 稳定后单独设计审批、幂等键和审计日志。
8. Docker、CI、演示视频和部署文档。
